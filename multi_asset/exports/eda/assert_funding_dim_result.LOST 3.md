## 发生了什么

2026-08-03 16:04:58 UTC, 我(B4)在给 `probe_funding_caliber_causal_v1.py` 打补丁做验证时截断了服务器上的这个文件, **536 B → 0 B**。

**根因**: Python **先求值实参**。`json.dump(..., open(path, "w"))` 里, 即使把 `json.dump` 替换掉, `open(path, "w")` 仍然在**求值那一刻**就把文件截断了。
> **打在"写"上的补丁, 保护不了被"打开"毁掉的文件。** 要重定向的是**写到哪里**, 不是**写不写**。

## 为什么它没有被自动重写

2026-08-03 的裁定是"不手工恢复, 由产出者(pilot_daily cron)明日自然重写, B4 核验"。**2026-08-04 核验结果: 没有被重写, 而且不会被重写。**

- 服务器上该文件仍是 `size=0`, mtime 停在截断的那一刻;
- `crontab -l` **没有**任何相关条目;
- `assert_funding_dim.py:390` 只在**它自己被调用时**写这个文件, 没有任何调度器调用它。

> **⇒ "cron 会重写它"描述的是一个不存在的机制。** 裁定本身没错, 错在**它的前提从来没有人去核**。

## ★★ 不要拿 git 里那份同名文件冒充它

`multi_asset/exports/eda/assert_funding_dim_result.json` 在 git 里**确实有内容**(253 B), 而**它不是被毁掉的那一份**:

| | git 里那份 | 被毁的那份 |
|---|---|---|
| 大小 | **253 B** | **536 B** |
| 日期 | `created: 2026-07-25` | 2026-08-03 |
| 面板 | `/var/folders/st/…/inject_sandbox_…/fixture/wide_dl_live.npz` — **macOS 注入沙箱的 fixture** | 服务器上的真实面板(未知) |

全部两个 git 修订都是 253 B(`707c7707` / `ef2ddbbb`), **没有任何一版是 536 B** ⇒ **服务器那份的内容无法从 git 复原。**

**⇒ 被毁那份说了什么, 现在无人知道。** 特别是: **不要**把 git 那份的 `verdict: "FAIL: ['funding_ema', 'xsr_fund', 'Y4']"` 读作被毁那份的结论 —— 那是**另一次运行、在另一张面板上**的结果。两份同名, 这正是它们最危险的地方。

## 现在该怎么办

- **不要**手工重跑去"补"一份放回原处: 内容即使忠实, 它的血统里也混进了事故响应, 而文件本身不会显示这一点(2026-08-03 裁定的理由, 仍然成立)。
- 若之后因为别的原因**正常地**重跑了 `assert_funding_dim.py`, 那份新产物是**新的**, 不是恢复; 把本文件改成指向它, 并保留上面的事故记录。
- **本文件存在的主要目的**: 让顺着 `See …` 指针来的人看到"**空文件 = 被毁**", 而不是"**空文件 = 从未产出**"。这两者在目录列表里长得一模一样, 而它们的含义完全相反。

> **一条错误信息里的 `see X` 是一个依赖: 它要求 X 存在且可读, 而没有任何东西检查这一点。**
> 指向本文件的那条信息在 `exports/eda/s1_artifacts/causality_serve.json` 里, 是**已冻结产物**(带 `.sha256` 侧车), 因此**不能**去改它的措辞 —— 所以这个悬空指针在**源头修不了, 只能在落点修**。本文件就是那个落点。
