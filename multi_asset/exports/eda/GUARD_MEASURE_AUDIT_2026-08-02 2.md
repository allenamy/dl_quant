# 1. §4-6 权重保真 —— **最紧急, 且昨夜的修复没有覆盖它**

## 1.1 度量分解

`corr = 1 − mawe × 100`, `mawe = mean_abs_weight_error`(每名字"应持权重 vs 实持权重"的平均绝对差), 判据 `corr < 0.85` **连续 3 个可判日**。可判性 = 该锚 `submitted > 0`。

**良性分量: underfill。** maker 挂 15 分钟后未成交部分过期, 书就到不了目标。仓库自己的注释算过: 每个"完全没有仓位"的名字贡献 `1/109 = 0.00917` 到 mawe, 即 **0.917 的 corr**;`corr < 0.85 ⇔ mawe > 0.0015 ⇔ 约 18 个名字完全没建上**。而在 15 分钟 maker 阶梯 + 约 50% 成交率下, **十几个名字没建上是正常结果, 不是故障。**

## 1.2 实测(6/6 锚全部越限)

| 锚 | mawe | corr | 限 0.85 | 可判(submitted>0) |
|---|---|---|---|---|
| 08-01 06:29Z | 0.009174 | **0.0826** | BREACH | 否(submitted=0, 按 eligibility 排除) |
| 08-01 12:00Z | 0.001983 | **0.8017** | **BREACH** | 是(94) |
| 08-01 16:01Z | 0.002206 | **0.7794** | **BREACH** | 是(80) |
| 08-01 20:00Z | 0.001929 | **0.8071** | **BREACH** | 是(91) |
| 08-02 00:01Z | 0.009174 | **0.0826** | BREACH | 否(submitted=0) |
| 08-02 04:00Z | 0.002423 | **0.7577** | **BREACH** | 是(96) |

- 两个 halted 锚的 `mawe = 0.009174 = 1/109` **恰好**是注释里描述的自锁形态, 已被 eligibility 正确排除 ✅。
- **4 个可判锚全部低于 0.85, 无一例外。最好的一次 0.8071, 距限还差 0.043。**
- **唯一挡着它的是"连续 3 个可判日"。08-01 是第 1 天, 08-02 是第 2 天 ⇒ 08-03 只要正常交易, 第 3 天到齐, §4-6 触发。**

## 1.3 为什么这是同一类, 而且昨夜的修复没盖住它

`position_break.py` 自己写过这两者的换算:
> `§4-6 judges corr = 1 − mawe·100 < 0.85, and mawe = break_frac / N, so §4-6's limit IS break_frac > 0.0015·N = 16.35% at N=109`

**⇒ §4-6 的等效仓位偏离阈值是 16.35%, 比 §4-5e 的 25% 更紧。实测 21.0–26.4% ⇒ 每个 rebalance 锚都同时越过两条线, 只是 §4-6 需要攒 3 天。**
同一份注释还写着设计意图: 「0.25 ... deliberately LOOSER than §4-6's implied per-observation limit: **a gate with no persistence requirement must not be able to fire on a book the persistent gate would accept**」。**这个意图现在失效了 —— 两条线都在书的下方, 不再是一松一紧, 而是一快一慢。**

# 3. §4-7 ops —— **两个半边的举证门槛差了两个数量级**

## 3.1 分解

`triggered = hit_rate OR drift`。

**(a) fail-rate 半:** `rebalance_fail_rate = n(venue_reject) / n(submitted 且非 skipped_min_notional)`, 限 **>5% 连续 3 天**。
`VENUE_SIDE_FAILURES = {"venue_reject"}`, 且 `OUR_OWN_RULES`(min_notional / spread / max_attempts)已被排除 ✅。**这一半是干净的**, 实测 08-01 与 08-02 均为 **0.0000**(370 / 179 单, venue_reject 0)。

**(b) drift 半:** `drift = bool(reconcile()["latest"])`, **无任何持续性要求 —— 最新对账锚上出现任意一条异常即为真**。

## 3.2 drift 的输入干净吗 —— **对 supersede 是干净的, 但对良性平仓不是**

**✅ 澄清一条你点名的怀疑: §4-7 的 drift 不受 supersede 污染。** `reconcile` 的 `signed_fills_by_anchor` 读的是 **orders 账本**而非 `fills.jsonl`, 且其 docstring 明确记录了这一点(并写明它在 08-01 的审计里「survived by luck of inspection」)。已核。

**❌ 但它对下面这些良性事件不是干净的**, 因为它的判据是 `residual = q2 − (q1 + Σ已记账成交)` 越过 `max(0.10×scale, min_notional)`:
1. **未入账的合法平仓** —— 与昨夜 §4-5b 完全同族;
2. **落在窗口边界另一侧的成交**(`_between` 按执行时间归窗)⇒ 一笔良性成交制造**两条**方向相反的异常;
3. **`filled_notional is None` 的行被跳过** ⇒ 该腿的成交完全不进 expected ⇒ 整额残差;
4. **`execution_of_unknown_size` 也算进 `latest`** —— 那是**测量缺口**(仓库实测历史上 101 条 `skipped_unknown_fill`), 却与真实的仓位失控进同一个布尔。

## 3.3 实测: 阈值坐在 p99 与 max 之间

7 个对账锚、160 个(锚×名字)比较:

| p99 | **3.540** |
| max | **9.560** |
| **典型阈值(min_notional)** | **5.000** |

**⇒ 阈值 5.00 正好落在 p99(3.54)与 max(9.56)之间。**

实际越限的 2 条, **都在同一个锚 08-01 20:00:51Z**, 而那是**六个锚里最健康的一个**(halt=False, calm, realized_gross 4081.89 / target 4297.77, 完成度最高):

# 4. §4-3 崩盘 markout —— **阈值正卡在两种口径的中间**

## 4.1 你点名的怀疑成立: 它的覆盖率项**没有折叠 supersede**

同一个循环里, 三行之内, 两种口径:

```
n_fills_seen  += len(PL.collapse_supersedes(one["fills"]))   # ← 折叠  (只用于"有没有输入"的叙述)
_m2_all = PM.m2_markout(one["fills"])                        # ← 原始  (all_marked / all_unmeasured)
f = [x for x in one["fills"] if x["anchor_ts"] in stress_anchors]
_m2 = PM.m2_markout(f)                                       # ← 原始  (mk_marked / mk_unmeasured, 判据用的就是它)
```

**判据用的那两个计数走的是原始行。** 而回填的机制是: 原行无 mark, 回填行**带** mark 且 `supersedes_trade_id` 指向原行 ⇒ **原始计数把同一笔成交同时记进"有 mark"和"无 mark"两侧**, 系统性地把覆盖率往 50% 拉。

## 4.2 实测: 同一份数据, 两个口径给出相反的判词

实盘树 720 条原始 fill 行 → **442 个唯一 trade_id**(278 条 supersede 行):

| 口径 | 覆盖率 | vs floor 0.50 |
|---|---|---|
| **原始行(现行判据所用)** | 278/720 = **38.6%** | **< 0.50 ⇒ DEGRADED** |
| **折叠后(真实)** | 278/442 = **62.9%** | **> 0.50 ⇒ OK** |

**`MARKOUT_COVERAGE_MIN = 0.50` 正落在 38.6% 与 62.9% 之间。**
分腿看(折叠后): maker 256/354 = **72.3%**, **taker 22/88 = 25.0%**。

## 4.3 危害方向 —— 是"红得没道理", 不是"绿得没道理"

覆盖率**不抑制 breach**(代码注释明确: coverage 只管"非 breach 能被读成什么")⇒ **这个缺陷不会让 §4-3 漏报**, 它会让 §4-3 在正常运行中**长期自称 DEGRADED**。危害是「重复告警训练操作员忽略告警」, 与漏报不同但同样要修。
**`worst_mk`(判据的那一侧)不受影响**: 未回填的原行不带 mark, 不进均值/极值, 每笔成交只以其回填行计一次。

## 4.4 另一件事: 它到现在**一次也没被行使过**

6 个实盘锚 **regime 全是 calm, `n_stress_anchors = 0`** ⇒ §4-3 处于 `NO_STRESS` 状态。**"没触发"在这里等于"没被考过", 这一条代码自己已经写死不许读成"市场很平静"** ✅。

# 6. 【交付 3】我的 §4-5e 拆分建议 (**未看 0B 的稿**)

## 6.1 判别量是**方向**, 而且必须逐名字算

现行度量在组合层取 `Σ|·|`, **绝对值当场销毁了符号信息, 而符号正是良性与危险的唯一判别器**。因此拆分必须发生在**每名字**层, 再聚合。

对每个名字 s, 设 `intended_s`(目标)、`prev_s`(锚前实持)、`venue_s`(锚后实持)、`submitted_Δ_s`(本锚提交出去的意图变动)、`filled_Δ_s`(已成交变动):

```
dev_s        = venue_s − intended_s                       (现行度量的被加项)
unfilled_s   = submitted_Δ_s − filled_Δ_s                 (我们送出去但没成交的那部分)
underfill_s  = clip(dev_s, 0, unfilled_s)   —— 取 dev_s 中**与 unfilled 同号且不超过它**的部分
unauth_s     = dev_s − underfill_s                        (剩下的: 没有任何"送出未成交"能解释)
```

- **`underfill_s`**: 我们朝目标走了、没走到。**良性, 是执行质量。**
- **`unauth_s`**: 反方向的偏离、超过意图的持仓、以及**根本没提交过订单的名字上的仓位**。**这才是"仓位失控"。**

## 6.2 两个门, 不同阈值、不同持续性、**不同动作**

| 门 | 度量 | 阈值来源 | 动作 |
|---|---|---|---|
| **执行质量门** | `Σ underfill_s / target_gross` | 从实测分布定, 现区间 21–26% ⇒ 建议**告警 40%**(留 1.5× 头顶), **不停机** | **仅告警**;同时作为 aim-portfolio 工作的输入 |
| **越权仓位门** | `Σ |unauth_s| / target_gross` | **紧**: 建议 **2%**, 因为任何越权敞口都是异常;**并加一条每名字绝对门 = 该 symbol 的 min_notional** | **停机, 无持续性要求** |

**要点: 现行的 25% 单门, 拆开后应当变成"一个更松的告警"加"一个远更紧的停机"。把它们合在一个数里, 必然只能取一个折中值 —— 而那个折中值对良性太紧、对危险太松, 正是昨夜发生的事。**

## 6.3 ★ 拆分本身会重建同一个缺陷, 除非明确处理 (我认为这是最容易被漏掉的一条)

`underfill_s` 的上界 `unfilled_s` 来自**订单账本**。**任何订单账本的记录缺口**(例如 `filled_notional is None`, 实测历史 101 条 `skipped_unknown_fill`)都会让 `unfilled_s` 偏小 ⇒ **该名字的偏离被错误地记进 `unauth_s` ⇒ 制造一个"越权仓位"停机。**

**⇒ 越权桶必须再分成两个状态, 而不是一个数:**
- `unauth_measured_s` —— 账本完整, 确实无法解释 ⇒ **进停机门**;
- `unauth_unmeasurable_s` —— 该名字的订单行缺少判定所需字段 ⇒ **进一个独立的"不可判"计数, 报告并告警, 但不进停机门**。

**否则我们只是把"良性 + 危险混在一个数里"降了一层, 变成"数据缺口 + 危险混在一个数里"——今天这一类的第 N 次。**

## 6.4 验收要求(按今天的教训, 不可省)

1. **先红后绿**: 必须构造两个 fixture —— (a) underfill 极大、unauth 为零 ⇒ 新门必须**不停机**;(b) unauth 单独越限、underfill 为零 ⇒ 新门必须**停机**。**且要先在未拆分的实现上验证 (b) 是红的**, 否则测试可能匹配不到任何东西。
2. **非对称输入**: 沿用 §4-3 `min`/`max` 那次的教训 —— 任何涉及极值/选择的测试, fixture 必须非对称。
3. **两个分量即使都不越限也要逐锚记录**, 否则看不到它们的漂移。
4. **§4-6 必须同时拆**(§1.3): 它与 5e 是同一个量的两种写法, 只修一个等于把同一个原因留在更慢的定时器上 —— **而那个定时器预计 08-03 到期。**
