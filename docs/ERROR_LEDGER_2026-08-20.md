**`(490 checks)` 这一串同时出现在 `ALL PASS (490 checks)` 与 `FAILURES: [...] (490 checks)` 两种结尾上。** 只引用计数**在两种结局下都成立** ⇒ **计数不是判词**。这与 [[battery_count_comparable_only_under_same_tree_state]] 同族, 但更尖: 那条说「计数只在同一树外状态下可比」, 这条说 **计数在同一次运行里就已经不区分通过与失败**。
**规矩**: 报告电池结果必须引**判词行整行**(`ALL PASS` 或 `FAILURES: [...]`)或**退出码**, **不得只引 `N checks`**。`tests_pipeline_gates.py:2832` 的 `sys.exit(1 if FAILS else 0)` 是对的 —— 退出码可信, 计数不可信。(我自己也差点栽在读法上: 我第一次把整条命令的退出码 0 当成套件的退出码, 其实那是管道里最后一个命令的。**管道会吞掉被测对象的退出码**。)

**那一格失败是什么**: 它断言 `merge_mwf_v4b.py` 的源码里**必须含有** `os.environ.get("V4_F8", "/workspace/f8_v4")` —— 即**要求**九月默认值那种写法。而那种写法正是 [[E-0918-O]] 的缺陷本体: 同一批默认值里 `V4_TRAINER` 落在 `/workspace/review_scratch/pod_f10_train_monthly_v4.py`(**被取代的旧训练器**), 并被写进封存模型 merge 收据的出处字段。**夹具把缺陷编码成了合同** ⇒ 谁修好了源码, 谁的套件就变红。
**这是同一天的第二个实例**: P-C1 第 [7] 节三个夹具设 `filled_known_notional=10` 同时 `filled_notional=25`(已闭合账本**物理上不可能**, 真实 46,363 行里 0 行), 它们为绿正是因为被测缺陷存在。⇒ **「绿套件」可以是「缺陷仍在」的证据**, 这是 [[suite_certifies_a_state_production_cannot_construct]] 的镜像形态: 不是套件认证了生产构造不出的状态, 而是**套件要求生产保持缺陷**。
**处置**: 断言已**反转为真实合同**并拆成三格 — ① 源码里**不得残留任何草稿目录默认值**, 全部路径走 `_req()`; ② `ENV_KEYS` 单一声明 + 收据记录每个键**解析成了什么**(出处可复核); ③ HF2 比较仍是信息性且其来源可选。链修复线其实**已经把 merge 装置改对了**(`review_scratch` 在新源码里为 0 次), 只是没发现自己顺手把这一格变红 — 因为它引的是计数不是判词。
**判别法**(加入验证形态学): 看见一格断言「源码里**必须含有**某个字符串」时, 先问 — **这个字符串描述的是我们想要的行为, 还是我们碰巧有的实现?** 若是后者, 这格会在修好缺陷时变红, 且它红得**没有信息**。
