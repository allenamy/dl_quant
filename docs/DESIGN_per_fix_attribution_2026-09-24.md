# 设计:逐修复项的书层归因(NC 相对 NEW_S)

## 0. 为什么需要它, 以及它不能回答什么

冻结件 §2 的「必报(不作门)」里有「哪项修复造成」。用户裁定 §2 也点名: **只做过单项臂可跑性, 没做逐项书层归因**。本设计是补这一项。

**它能回答**: 去掉某一项修复(其余保持 NC 现状), 判据窗的日收益差相对完整 NC 变化多少。
**它不能回答**: 「NC 与研究员 NEW 的缺口由什么造成」—— 那是另一个对象(见 §6)。

## 3. /dev/shm 预算 —— 实测值, 不是估计

| 量 | 实测 |
|---|---|
| 当前空闲 | **约 2.3 GiB**(03:0xZ) |
| 一个引擎 run 目录(单格) | **0.337 GiB** |
| 一次 `bt_launch --resume`(5 格) | **1.685 GiB** |
| 目标 npz(单种子) | 0.026 GiB |
| 特征包 | 2.757 GiB, 但是**对 nc 根的硬链接**, 不额外占用 |

**所以完整 5 格 × 7 臂 = 11.8 GiB, 放不下。** 两条对策:

**方案 A(推荐)——「只跑 base 格 + 逐臂跑完即腾」**
- 归因用的是判据窗日差点估计, 只需要 `base` 格; 成本格(fee/slip/fill)与 `lit` 是 A 门 S5 的材料, 归因不需要。
- 每臂峰值 = 0.337(引擎)+ 0.026(目标)+ 重放中间件 ≈ **0.5 GiB**;
- 跑完读出数字 → 核 sha → 腾掉该臂的 runs → 下一臂。**峰值不叠加**。
- 需要改配置的 `runs` 列表只留 base 一项 —— 这是对运行配置的改动, 须 lead 点头(见 §5 预注册)。

**方案 B ——「先腾再跑全格」**
- 我自己的可腾项(只限我自己的, 逐项按收据核过 sha 再删):

| 可腾 | 大小 | 核法 | 风险 |
|---|---|---|---|
| `work/king_run1_wrongenv`, `work/king_run3_syspy_envset` | 0.092 GiB | 二者的比较结论已在 `KING_ENV_SENSITIVITY.json`(含逐数组结果), 删后结论不依赖它们 | 低 |
| `runs/NEWS2_s2027*`(6 目录) | 2.02 GiB | 判词已出、读数收据已落盘且 `UPSTREAM_MANIFEST_POST` 记有逐文件 sha; s2027 未放行部署 | **中**: 若 lead 日后要复核 s2027 的路径级数字, 需重跑引擎(约 55 分钟) |
| `runs/NEWS2_s42X`, `NEWS2_s2027X`(2 目录) | 0.684 GiB | 只被 `ext` 描述段用过, `NEWS2_EXT.json` 已落盘 | 低 |

- 全腾 = 2.8 GiB, 空闲到约 5.1 GiB, 仍不够 6 臂 × 1.685 GiB。所以**方案 B 单独不成立**, 只能作为 A 的补充余量。

## 4. 每臂的判读(预注册, 先于任何数字)

对每个臂, 报 **相对完整 NC** 的判据窗(2023H2 / 2024 / 2025)合并日收益差:

- `d_arm = mean_daily(arm) − mean_daily(NC_s42)`, 口径与 B1 完全相同(`news_stats.py` `7141ba42` 的 `dbar`);
- 同时报 30 日块 97.5% 区间, **照冻结件原句附「本规则是换装决策规则, 不是统计显著的声明」**;
- **不设门**。本项是必报诊断, 不产生录取/否决。

**预先声明三件事, 免得看到数字后再解释**:
1. `d_arm > 0` 意味着「去掉这项后更好」, 即该项**拖累**书; `d_arm < 0` 意味着该项**贡献**。
2. 六个 `d_arm` **不可相加**。本项目已有受据结论: 留一之和与总量不符(留一不可相加/有交互)。所以本表**不得**被读成分解。
3. 若某臂的区间跨零(预期多数会), 结论就是「在这台仪器上分辨不出」, 不是「作用为零」。
