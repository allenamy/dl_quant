# 团队协作协议 (TEAM_PROTOCOL)

**为什么存在:** 2026-08-03 单日发生 3 类协作故障, 合计浪费 5.5 小时并两次让 team-lead 拿错误信息对用户发言。**每一条规则后面都附了产生它的事故** —— 一条没有事故的规则会被下一个人当作官僚主义删掉。

**适用:** team-lead 与所有 subagent 会话。**每次派工必须引用本文件路径。**

---

## 1. 完成必须被声明

> **一个完成了却没被声明的交付, 与没完成, 在 team-lead 这里不可区分。**

- **报告先于空转。** 任何 subagent 在停止工作前**必须**发出一条报告消息。空转通知(idle)**不是**报告, team-lead **不会**把它读作"做完了"。
- team-lead 的对应规则: **对纯 idle 通知不回应**, 只在有内容时回应。
- 报告最少含: 改动了盘上什么 / 验证了什么 / **没有**验证什么 / 你认为还没被任何断言覆盖的风险点。**最后一项最重要, 且只有执行者知道。**

*事故: 08-03 两个会话完成工作后空转不报(PREREG 43KB 已落盘 / 停机门接线已提交且电池全绿), team-lead 靠翻磁盘才发现, 期间正准备据此做部署决定。*

## 2. 任务必须有具名 owner —— 不存在"后继会话"

> **向一个不存在的角色交接, 等于把工作扔进虚空, 而且看起来像交接成功了。**

- 交接**一律交给 team-lead**, 由 team-lead 重新派给一个**具名会话**。
- 禁止写"交我的后继会话"/"下一个人来做"。
- team-lead 的对应义务: 维护 `STATE.md` 的 owner 表; **一个任务没有 owner 就不是任务, 是愿望。**

*事故: 08-03 06:03Z 构建会话交接"B 接线交我的后继会话", 而后继会话从未被创建; 规格齐备、红测齐备、口头复述三次排期, 但 5.5 小时零进展, team-lead 在锚前 27 分钟才发现。*

## 1-b. "我已修好 X" 必须由他人对第三方基准复验

**凡"我已修好 X"要落进永久记录(journal/STATE/判决), 由另一个会话用【不同命令、对第三方基准】复验一次, 复验先于记录。** 自查不够: 报告自己的动作时, "意图"会冒充"结果", 且没有第二个人是天然核对方。

*事故(同日两面): (a) team-lead 首次 scp 静默拷 0 文件而 journal 已写"托管已修"(把动作意图当结果, 报告自己); (b) C2 把"team-lead 已派…加断言"写进冻结文档而未 grep(把状态转述当前提, 引用别人)。两次都是"声明先于观测"。正例: C2 对托管修复未读声明, 直接三方比哈希(git HEAD blob = 工作树 = 服务器原件, 两层设计排除"内容不同"与"版本过期"两种假绿), 9/9 过后才闭合。*

## 3. 消息交错的处置

异步信箱必然交错。规则不是避免交错, 是让交错**可检测、可收敛**:

- **执行者**: 收到新指令时, 若手上有未发出的报告, **先发报告并标注 `[与你的指令交错]`**, 再读新指令。**不要在报告里合并两轮内容。**
- **裁决者**: 检测到交错时, **用一条消息重述当前生效的全部指令**, 不要逐条追溯谁先谁后。
- **裁决者**: 同一个 agent 有未回报告时, **不发第二条实质派工**(HALT 除外)。
- 双方: 引用对方消息用 msg id, 不用"你上一条"。

*事故: 08-03 至少 6 次交错, 导致重复汇报、重复裁定、以及一次"我已经裁过了"的往返。*

## 4. 引用前必须打开看

> **引用一份文档为权威来源之前, 打开它, 读首行状态。**

- 交接**只能引用刚核实过是最新的产物**; 优先引**不可变锚点**(commit SHA / 文件 SHA-256 / 验收时间戳) —— **SHA 不会过期, 只会不完整。**
- 若必须引可变文档, **更新它是交接前的最后一个动作**。

*事故一: 08-03 05:0xZ 交接指向 journal, 而该文件停在 2 小时前, 之后的全部内容(锚点结果/门 PASS/两次裁定)一条不在。*
*事故二: 08-03 13:xxZ team-lead 把一份首行写着 `SUPERSEDED — 不得据此执行复现` 的指南当权威来源给了执行会话, 而给的时候没打开看。**同一天同一个错, 第二次, 犯的人是立规则的那个。***

## 4-b. 演进中的文档, 引"链"不引"点"

派工引用一份**仍在演进**的文档时, 引 **现行文件名 + 侧车哈希链**, 由执行者核对链顶并**在回执里声明所据版本**; 不引点哈希 —— 点哈希只对已冻结产物有效, 对演进中的文档它是一张**会在你手上过期的快照, 且过期时看起来仍然像锚点**(§4 的"SHA 不会过期"前提在这里不成立)。

**判据(不靠判断力):** 该文档若有 `.sha256` 侧车且其 `chain:` 多于一行 ⇒ 它是演进中的 ⇒ 引链。
**执行者义务:** 若所据版本与派工所引不同, **动手前**声明并给喊停机会, 不是事后在报告里提。

*事故: 08-03 15:35Z 派工引 v1 点哈希, 而 v2/v3 于 15:39/15:42Z 相继冻结; 执行者收到时链顶已换, 且约束它的条款(b)已被更正。执行者(B4)的处置成为本条的正例。*

## 5. 上下文预算尾声只做交接

- 接近上下文上限时**不要再挤一件工作**, 把交接写干净: 已闭合结论+各自 SHA / 未完成项+**确切阻塞点** / 复算命令 / **不要重走的弯路**。
- **所有 SHA 在写交接前逐一重算, 不得从记忆引用。**

*正例: 08-03 审计会话主动声明预算耗尽并按此交接, 交接文档经 team-lead 独立复验哈希相符。*

## 6. 实盘系统的三条硬约束

- **落盘即上线**: `~/dl_quant_live` 的工作树就是 launchd 的运行目录 —— **写入文件的那一刻就已生效, 不需要 `git commit`。** 预备性改动必须在分支上做。
- **一锚一变更**: 每个锚点最多带一个行为改动, 否则异常无法归因。
- **改动前后必须跑完整验收电池并贴出读数**; 未全绿不得声称完成。

## 7. 结论纪律(与 [[verification-failure-morphology]] 记忆互补, 这里只列协作相关的)

- **模式匹配的结果是候选, 不是发现** —— 逐个读过原文才升级。派工方对应: 不把候选派成任务。
- **凡报告一个相关/比值, 必须声明它的聚合维度**(逐锚横截面 / 池化 / 时序)。*事故: 池化 0.84 被用来回答横截面的问题, 并经 team-lead 转述给用户。*
- **前提未确证不跑主实验。**
- **拿不准的口径停下问, 不要自己选一个看起来对的。**
- **一致性锚点对不上时照实报, 不得调和** —— 调和之后所有数失去意义, 而且看起来像成功。
