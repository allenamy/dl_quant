# 修订 1: 缺口占比的单位,以及分母的可行性

lead 2026-09-24 批准原文 58a29c04a 执行,并补两点。本文把它们落成文字,**写在跑任何臂之前**。

## 1. 主读数单位改为 bps/日;夏普差降为旁报

原文 §3 主读数用 pre-2026 **路径均值夏普**算 `(NEW − 臂) / (NEW − NC)`。lead 指出冻结件的同口径量是 **bps/日**,
并口述 NC 对 NEW 大约 **2.8 / 0.9** bps/日。改为:

- **主读数:`(NEW − 臂) / (NEW − NC)`,分子分母都用 pre-2026 配对日差,单位 bps/日。**
- **旁报:同一比值用 pre-2026 路径均值夏普,单位「夏普点」。** 原文给的 0.42(s42)/ 0.14(s2027)**是夏普差**,
  本文据此明确:那两个数的单位是夏普点,不是 bps/日。原文没写单位,这是原文的缺陷,本文补上。
- **两种单位都报,并排。** 任何一处引用占比都必须同时给出**分子的绝对值与它的单位**。
  原文那条"不得单独引用占比"的纪律继续有效,并扩展为"不得在不写单位的情况下引用占比"。

## 2. 新增可行性事实:bps/日 的分母**不存在于任何收据**,必须由我现算

逐个打开三份判词收据核过:`OVN_STATS.json` 把 NEW 对 **OLD / OLD_HOLD** 比,`NEWS2_STATS.json` 把 NC 对**它自己的对照**比。
**没有任何收据含 NEW 对 NC 的配对日差。** 所以分母必须从两组运行目录直接算配对日差。

已核实它算得出来,且算出来是干净的:

| 事实 | 实测 |
|---|---|
| NEW base 格路径数 | `ovn/runs/OVN_NEW_s{42,2027}_scaled_rule_raw_UAFE` 各 32 个 `PATH_*.npz` |
| NC base 格路径数 | `news2/runs/NEWS2_s{42,2027}_scaled_rule_raw_UAFE` 各 32 个 `PATH_*.npz` |
| 四条臂的引擎钉 | `device_sha256` / `calibration_sha256` / `price_pin` 三者**各只有 1 个不同值,全同** |

⇒ NEW 与 NC 是**同一台引擎、同一标定、同一价格钉**下的两组运行,按种子 k 对 k 配对是合法的配对差,
与我在 FRESH 那轮对 NEW_S 做的配对方式相同。

## 3. 新增前置门(不替换原文任何门,只追加)

| 门 | 内容 |
|---|---|
| **P0b 分母同引擎** | NEW 与 NC 两组 base 格的 `device_sha256` / `calibration_sha256` / `price_pin` 必须一致(已预核为一致,执行时重核并写进收据)。不一致 ⇒ 分母不是干净配对差,照报但在结果里点名降级为"跨装置比较"。 |
| **P0c 分母口述值对照** | 算出 NEW − NC 的 pre-2026 配对日差(bps/日),与 lead 口述的 **2.8 / 0.9** 对照。**这是对照不是断言** —— 口述带"大约",所以不设容差、不因偏离而停;但若偏离超过 20%,必须在结果里点名并给出我算的值与口径(段、天数、路径均值定义),让 lead 判断是谁的口径不同。 |

**为什么 P0c 不写成断言:** 把一个口述的约数焊成断言,会在正确数字上变红,而最省事的修法是放宽它 —— 那就回到假绿一族
(`brittle_check_welds_identity_to_population_expectation_2026_09_20`)。所以它是"报告 + 超限点名",不是门。
